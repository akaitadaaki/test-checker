# test-spec: Test Checker 用テスト仕様書の作成

Test Checker は、Markdown のチェックリストを手動テスト仕様書として読み込み、
結果(PASS/FAIL/SKIP/要再確認)を別ファイルに記録する macOS アプリ。
このスキルは **アプリが読める形式で、抜けの少ないテスト仕様書を書く** ためのもの。

## 出力フォーマット(厳守)

```markdown
---
project: <プロジェクト名>
---

# <機能名>

## 正常系

- [ ] <PREFIX>-001 <1行で分かるタイトル>
  - 手順: <操作を具体的に。画面名・入力値を含める>
  - 期待: <観測できる結果。画面・メッセージ・データの状態>
- [ ] <PREFIX>-002 ...

## 異常系

- [ ] <PREFIX>-101 ...

## 境界値

- [ ] <PREFIX>-201 ...
```

ルール:

1. **1行 = 1ケース**。行頭は `- [ ] ` (列0から。インデントしない)。
2. **ID 必須**。形式は `英字で始まる英数字_` + `-` + `数字` (例 `LOGIN-001`, `API_V2-010`)。
   - 機能ごとに PREFIX を変える。番号は 正常系 0xx / 異常系 1xx / 境界値 2xx / 権限・セキュリティ 3xx / 表示・文言 4xx を目安にする。
   - **既存の ID は絶対に変えない・再利用しない**(過去の結果と紐付いているため)。追加は末尾の番号を進める。
3. ケース直下に **`- 手順:` と `- 期待:`** をインデント(2スペース)して書く。1ケースに期待は1つ。複数の観点があればケースを分ける。
4. 見出し `#`/`##` でグループ化する。見出しはアプリの一覧に表示される。
5. front matter の `project:` は必ず書く。
6. `- [ ]` で始まらない箇条書きはテストケースではなく補足として扱われる。コードブロック内の `- [ ]` は無視される。
7. タイトルは「〜できる」「〜が表示される」「〜でエラーになる」のように **期待が読み取れる文** にする。

## 手順

1. **入力を集める**: 対象機能の説明、既存の仕様書(あれば `*.md` を探す)、関連コード、PR 差分、画面一覧。
   不明点(対象環境、権限ロール、境界値の具体値)は推測で埋めず、仕様書冒頭に `<!-- 要確認: ... -->` コメントで残して依頼者に質問する。
2. **観点を洗い出す**(最低限これを検討する):
   - 正常系: 主要な操作フロー、代表的な入力
   - 異常系: 未入力・不正形式・重複・存在しない対象・通信/サーバエラー
   - 境界値: 文字数上限±1、0 件/1 件/大量、日付の境目、数値の最小/最大
   - 権限: 未ログイン、権限なしロール、他人のデータ
   - 状態遷移: 二重送信、戻る操作、途中離脱、再読み込み
   - 表示: 文言、レイアウト崩れ(長文・多言語)、ローディング/空状態
   機能に関係ない観点は無理に書かない。依頼された機能の範囲外のケースは、必要だと思っても追加せず、報告時に提案として伝える。
3. **既存の仕様書に追記する場合**: 既存の ID・タイトル・見出しは変更せず、該当見出しの末尾に新しい ID で追加する。
   削除が必要なケースは消さずに `## 廃止` 見出しへ移動する(結果履歴を残すため)。
4. **書き出す**: 上記フォーマットで `<機能名>.md` に保存する(既存ファイルがあればそれを更新)。
5. **検証する**: `python3 <このスキルのディレクトリ>/scripts/lint_spec.py <file.md>` を実行し、エラーが 0 になるまで直す。
   lint は ID の重複・形式、`- [ ]` の位置、手順/期待の欠落、front matter の有無を検査する。
6. **報告する**: ケース数(見出しごと)と、`要確認` として残した点を箇条書きで伝える。

## 良い例 / 悪い例

```markdown
- [ ] LOGIN-101 存在しないメールアドレスでログインするとエラーになる        ← 良い: 入力と結果が分かる
  - 手順: ログイン画面で `nobody@example.com` / 任意のPWを入力し「ログイン」を押す
  - 期待: 「メールアドレスまたはパスワードが違います」と表示され、画面遷移しない

- [ ] ログインのテスト                                                     ← 悪い: ID なし、何を確認するか不明
- [ ] LOGIN-001 正しく入力するとログインでき、ダッシュボードが出て、通知も出る   ← 悪い: 期待が3つ。3ケースに分ける
```

## 保存場所の目安

テスト対象プロジェクトの `docs/tests/<機能名>.md` など、**仕様書とその結果フォルダ(`<機能名>.results/`)を
一緒に Git 管理できる場所** に置く。依頼者が場所を指定していなければ提案して確認する。
